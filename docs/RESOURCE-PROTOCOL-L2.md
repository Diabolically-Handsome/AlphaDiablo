# L2 战备门与原生城镇补给协议

版本：`l2-town-v1`。日期：2026-09-04。本协议是完整通关目标中的 L1→L2 工程与机制验证阶段；没有证明模型已具备连续打通 16 层的能力，也不为 L3–16 提供已校准战备标准。所有效果结论须由冻结实现上的零训练探针产生，本文件不预填胜率或训练建议。

## 接口和默认行为

`OptionsEnv`、`WorkerWindowEnv` 及训练 `make_env` 接收：

```python
resource_protocol="off"          # "off" | "l2-town-v1"
resource_purchase_mode="full"    # "none" | "heal" | "potions" | "armor" | "full"
```

`train/train_ppo.py` 与 `train/eval_assembled.py` 提供同名 CLI 旗：`--resource-protocol`、`--resource-purchase-mode`。CLI 默认 `off/full`，关闭协议时不允许单独改变购买模式。训练入口只允许在 `--worker` 或 `--options` 环境中启用；旗的暴露不代表本次获准启动训练。本次新增训练步骤为 0。

开启协议后改变的是原生换层权限、补给服务及其记账，工人仍使用现有 15 动作与原观测视图。原生 `resource_state` 供经理、服务控制器和审计使用，不向冻结工人悄悄追加观测维度。协议与购买模式进入实验身份。当前服务配方标识为 `l2-town-paid-repair-v2`；评测元数据、训练契约和探针配置显式记录各臂阶段顺序，防止将维修前后的 `full` 混称同一处理；源码 bundle 包含 `python/diablogym/resource_protocol.py`。

关键桥接口为 `configure_resource_protocol`、`configure_town_service`、`act_pickup_gold_at`、`act_talk_towner`、`act_dismiss_dialog`、`act_buy_store_item` 、`act_equip_inventory_item` 和 `act_repair_equipped_item`。购买与穿装备请求同时绑定索引及 `seed_hi/seed_lo/create_info/base_id`，拒绝过期或错位目标。`probe_resource_*` 是原生测试夹具，零训练游戏探针不调用这些改状态接口。

## 硬门是待验证假设

L1→L2 的最终许可由 C++ `EvaluateResourceReadiness` 与玩家原生换层入口决定，Python 不重新拼装一把近似尺子。当前所有条件必须同时成立：

| 条件 | L2 入场阈值 |
|---|---:|
| 角色等级 | ≥ 2 |
| 原生护甲值 | ≥ 9 |
| 当前最大物理武器伤害加角色伤害修正 | ≥ 6 |
| 当前生命 | ≥ 最大生命的 80%，使用原生定点整数交叉相乘 |
| 腰带即时治疗物品 | ≥ 4 |
| 头、双手、胸部已装备物品中的有限耐久最小值 | ≥ 15 |
| 可用且未损坏的已装备武器 | 至少一件 |

这些数值是第一轮可证伪假设，不是安全保证。生命、命中、抗性、围攻情境和未来资源消耗仍可能使达标角色死亡。实际首轮 smoke 暴露了旧剑盾耐久不足，因此经授权将普通付费维修加入 `full` 臂。维修仍受实际金币、原生价格、装备身份及耐久上限约束；达不到标准时应报告具体经济缺口，不能据此宣称 RL 不愿推进，也不能为获得下楼数静默降低阈值。

经理、工人权限和原生入口执行同一许可结果。`cleared`、FARM 场景上限或 `exhausted` 不再豁免未达标下降。`DIVE` 包含剧情操作和任务副本返回，因此不能用战备不足封死整个 DIVE 语义；新主地牢下降由原生目标类型和深度另行检查。本轮禁止进入 L3+，禁止未授权回城与未支持的传送/捷径。

## 补给闭环与失败边界

服务只支持 **主地牢 L1→城镇→同一 L1**，每局至多发起一次。在战备未达标且已清场或累计 FARM 场景微拍达到 3600 时进入资源处理；不以 140 拍 idle/exhausted 作为回城许可。流程包括已见金堆扫金、原生楼梯步行、按臂购买/维修、Pepin 治疗和返回原 L1。`armor/full` 先到 Smith；`full` 按需买甲并穿上后，维修仍装备在身且阻碍耐久门的物品，再到 Pepin 治疗和用余额购药。`heal/potions` 只到 Pepin。这个路由避免反复往返两个 NPC，600 微拍上限不变。

服务独立总预算为 600 微拍，包含步行、对话、购买、换装和动作结算。所有真实 `bridge.step` 都计入本局时间；`finish/complete` 为零微拍服务事件，不伪装成学习工人的等待动作或额外扣停滞费用。来回城镇不重复支付已到达层数的奖金，返回原 L1 保留该场景的探索/战斗记账，不能利用旧怪或旧格再次领取首次收益。

服务返回但未达标时，若尚有可清理敌人或可执行的拾药/换装机会，可以继续 FARM；一次行程资格不会重新开放。无可执行改善路径、商店不可用、路径失败或服务超时都要保留具体资源失败原因，不自动放行，不通过无限干等获得“存活”。

## 本次无头商店实际修复

本次将标准文字商店的购买/维修提交核心与 Gym 共用；独立的 `visual_store` 界面本批未重构。为无头调用补全接近 NPC、打开商店、显式结束任务对话、购买和从背包装备护甲的路径。Pepin 可能先给毒水任务对话；脚本必须显式关闭对话后继续真实治疗，不能直接改生命值。

商店报价仅在相应 NPC 商店打开时供服务读取。报价与容量查询保持只读；过期物品、金币不足、无空间等拒绝不消耗金币、不改库存且不消耗 RNG。成功购买通过原生支付和放置逻辑完成；若护甲进入背包，再按完整身份穿上，并把旧甲保留在背包中。护甲门已满足时跳过无必要的购买。购药臂在预算和腰带空位允许时最多补至 8 个治疗物品，硬门最低数量仍为 4。

维修调用与正常商店共用原生价格和支付内核，不用战士维修技能，不免费改耐久。只维修 `full` 臂中仍装备在身、当前耐久不足 15 且正常修复可达到 15 的物品；换下的旧甲保留但不修。报价只在 Smith 处读取，按价格和装备槽顺序尝试，缺钱或原生拒绝均记失败原因。维修次数/费用与买物次数分开报告，总金币消耗同时包含两者；不远程读取 Pepin 价格，不保证预留买满八瓶的钱。

范围暂不包括卖物、传送门经济、法术/武器购买、其他商人或 L2 以上往返。服务是明确披露的脚本辅助，不能把其行为计为冻结工人的学习成果。

## 五臂与固定曝光评测

`train/probe_resource_protocol.py` 固定使用现有 R16 工人和已消费种子 `2114000–2114047`。五臂共享硬门、采样方式、逐局种子、单线程 Torch、工人视图和经理规则：

| 模式 | 行为 |
|---|---|
| `none` | 扫金；不回城、不购买 |
| `heal` | 扫金和同一路线回城；免费治疗，不买物品 |
| `potions` | 回城治疗并买药 |
| `armor` | 先 Smith 按需买甲/装备，再 Pepin 治疗，不买药、不维修 |
| `full` | Smith 按需买甲/装备和正常付费维修，再 Pepin 治疗和余额购药 |

从正常地牢开局计时，首次到达 L2 的预算为 **6000 微拍**。首次实际 L1→L2 换层后，给予完整 **1800 微拍** 跟随观察，因此绝对上限为 **7800 微拍**。时钟由每次真实原生微拍回调更新；城镇行程不暂停计时，任务副本另记场景，初次开局进入 L1不算 L2 到达。

主结果是“预算内实际到达 L2，且首次到达后 1800 微拍仍存活”的联合成功。未到达、资源失败和到达前死亡均不成功；存活但观察不足记未知/删失，不能算成功。完整探针若出现这种删失即报告工程失败。另报实际 L2 暴露、到达时间、战备短板、服务成本、资源失败和配对种子成功差。

硬门会使不同臂进入 L2 的样本不同。因此各臂“已下楼者存活率”只能作为选择后的描述，不能直接解释为药或甲的纯生理效应。五臂首先比较补给策略的总体效果。是否能进一步拆解纯药/甲效应，需要所有分支均符合相同硬门的真实可达公共状态，另行设计试验。

旧 `probe_r17_deployment.py` 的存活截断报告已修正：不足首次下楼后 1800 微拍的存活终止返回 `None`；汇总单独报告删失数，观察分母排除未知值。原有档案没有覆盖重写，也不会冒充已重新跑出的结果。

## 隔离候选与运行方式

原仓库和原生库先快照保留。施工与验证目录为 `/home/laure/r18_resource_20260904/`；`snapshot/` 保存回滚证据，最终 `build-v4/` 是隔离原生库，`candidate-v4/` 是冻结代码镜像。较早候选及其失败现场保留用于追溯。候选目录不自动跟随源代码；已有评测目录不得更新，后续修改应创建新的候选及输出目录。

在候选镜像中运行，不替换原仓库的 `build/`：

```sh
cd /home/laure/r18_resource_20260904/candidate-v4
PYTHONPATH="$PWD/python" .venv/bin/python train/probe_resource_protocol.py \
  --phase smoke \
  --output-dir /home/laure/r18_resource_20260904/reports/smoke-v4-reproduction
```

smoke 包含 16 个 R16 游戏种子、同 16 种子逐局重复以及 16 个认证工人独立复核。除了无工程异常和逐局重复一致，两个模型各须至少完成一次实际 L1→town→L1 往返，且服务以 canonical ready 的 `complete` 结束。16 局均未触发商店或均死亡不能假通过覆盖门。

只有同一实现/原生库/模型身份的 smoke 为 PASS 后，才能运行：

```sh
PYTHONPATH="$PWD/python" .venv/bin/python train/probe_resource_protocol.py \
  --phase pilot \
  --engineering-receipt /home/laure/r18_resource_20260904/reports/smoke-v4-reproduction/summary.json \
  --output-dir /home/laure/r18_resource_20260904/reports/pilot-v4
```

输出目录必须不存在。驱动保存配置、原生与模型身份、逐局 JSONL、重复轨迹、认证复核、失败现场及汇总。只读记录进入城镇时的原有 raw 快照、商店库存内容变化及服务阶段变化时的微拍/位置；raw 未导出 RNG 时明确记录为空，不额外调用 observe。PASS 是相应执行/覆盖门通过，不等于模型能力认证，更不自动授权续训。
